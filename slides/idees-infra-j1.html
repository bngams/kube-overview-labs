Tout est installé à la main sur une seule VM. Faire imaginer le manuel de déploiement. Scaling vertical facile, horizontal difficile (et la base ?). Les éléments en pointillés n'existent pas : c'est ce qu'il faudrait concevoir pour la haute disponibilité.
Scénario fictif mais très réaliste : un ancien composant .NET Framework impose un Windows Server. Deux OS, deux manuels, des adresses IP en dur entre les VM.
Le registre apparaît. Le déploiement devient « installer le runtime, docker compose up ». On peut dupliquer les conteneurs sur la machine, mais il faut un reverse proxy pour router. Toujours une seule machine.
Une fois conteneurisés, db et result (images Linux) rejoignent la VM Linux. Piège classique : une image Linux ne tourne pas sur un hôte Windows ; la VM Windows reste tant que le worker n'est pas porté.
C'est exactement l'environnement de nos TP : parfait pour apprendre, pas pour la production. On gagne l'auto-réparation et les mises à jour progressives, pas la haute disponibilité.
Exemple sur site avec Rancher (open source, SUSE) et RKE2. Le plan de contrôle est toujours sous Linux ; un nœud Windows accueille le worker grâce à nodeSelector. Passer en revue les 6 décisions à gauche.
