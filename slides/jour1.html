Module 1

Pourquoi les conteneurs ?

45 minutes. Démo formateur possible : lancer la même image sur deux machines.

Une application, c'est quoi ?

Une application ne tourne jamais seule : elle dépend d'une pile entière. Chaque couche a sa version et sa configuration.

« Ça marche sur ma machine… »

Et maintenant : 50 serveurs, 3 environnements, des mises à jour chaque semaine…

Le grand classique. Demander : qui a déjà vécu ça dans un projet ? Les écarts d'environnement coûtent cher en recette.

La réponse : livrer l'application avec son environnement

Comme le conteneur maritime : une boîte standard, quel que soit son contenu, que tous les ports savent manipuler.

Le conteneur contient l'application et tout ce dont elle a besoin. La métaphore du conteneur maritime : standardiser l'emballage, pas le contenu.

Conteneur ou machine virtuelle ?

Machine virtuelleConteneur
Poidsdes Go (un système complet)des Mo (l'application et ses dépendances)
Démarragedes minutesdes secondes
Isolationtrès forteforte, mais le système est partagé
Les deux coexistent : en pratique, les conteneurs tournent souvent dans des machines virtuelles chez le fournisseur cloud.

Module 2

Image, conteneur, runtime

Rester léger : pas de namespaces Linux ni de cgroups. Juste la bonne représentation mentale.

La recette, le plat, l'assiette

Une image, plusieurs conteneurs. Exemple du cours : ghcr.io/bngams/kube-vote:1.0 = registre / nom / version (tag).

On construit l'image une fois, on la range dans un registre, n'importe quelle machine peut la récupérer et en lancer des conteneurs.

Une image est faite de couches

Une mise à jour ne télécharge que ce qui change : c'est pour cela qu'elle est rapide.

Vu en vrai au TP01 : au téléchargement de la v2, les 4 premières couches affichent « Already exists ».

Qui fait vraiment tourner le conteneur ?

Kubernetes décide quoi lancer et où. Le runtime sait comment.

Kubernetes n'a pas besoin de Docker : il parle à un runtime (souvent containerd) via une interface standard. Mais les images sont les mêmes : une image construite avec Docker tourne telle quelle dans Kubernetes.

Module 3

Un conteneur ne fait pas une plateforme

30 minutes. Construire le schéma en direct sur Excalidraw si possible, en partant du constat de fin de TP01.

Notre application de vote

5 morceaux, 3 langages, 2 bases : comme beaucoup d'applications d'entreprise.

Présenter le fil rouge. Chaque morceau dans son conteneur. Question : comment fait-on tourner tout ça, en vrai, en production ?

Les vraies questions de la production

  • L'API plante à 3 h du matin. Qui la redémarre ?
  • Le serveur tombe en panne. Où relancer les conteneurs ?
  • Le trafic triple. Comment passer de 1 à 5 exemplaires ?
  • Comment livrer une nouvelle version sans coupure ?
  • Et revenir en arrière si elle est cassée ?
  • Comment les morceaux se trouvent-ils, quand ils changent de serveur ?

Docker sait lancer des conteneurs. Il manque un chef d'orchestre.

Faire répondre la salle à chaque question. Rappel TP01 : après /crash, le conteneur est resté arrêté.

L'orchestrateur

Un programme qui pilote des conteneurs sur un ensemble de serveurs (un cluster) : il les place, les surveille, les répare, les met à jour, les relie entre eux.

Kubernetes

Le standard de fait. Proposé par tous les clouds.

Les autres

Docker Swarm, HashiCorp Nomad, AWS ECS… plus simples, beaucoup moins répandus.

Kubernetes (« timonier » en grec, souvent abrégé K8s) : ouvert par Google en 2014, inspiré de son outil interne Borg, confié à la CNCF en 2015.

Pourquoi K8s a gagné : open source, neutre (CNCF), soutenu par tous les clouds, écosystème énorme. Le documentaire (ressources) raconte cette histoire.

Module 4

Kubernetes : l'état souhaité

Le module le plus important du cours. Prendre le temps.

Donner un ordre… ou un objectif ?

🔧 Impératif : un ordre

« Allume le radiateur. »

Il chauffe… puis plus personne ne surveille. Fenêtre ouverte ? Tant pis.

docker run …

🎯 Déclaratif : un objectif

« Je veux 20 °C. »

Le thermostat mesure en permanence et ajuste tout seul.

Kubernetes

Kubernetes est un thermostat pour applications.

L'analogie du thermostat fonctionne très bien auprès des non-techniques.

La boucle de réconciliation

L'idée centrale. Une panne, une erreur, un serveur qui redémarre : ce ne sont que des écarts à corriger. Vu en vrai au TP02 : on supprime un pod, il revient.

Comment est fait un cluster ?

Dans un Kubernetes managé (EKS, GKE, AKS…), le fournisseur gère le control plane. Votre cluster de TP n'a qu'un nœud, qui fait tout.

Rester haut niveau. Sur chaque nœud, un agent (kubelet) dialogue avec le runtime vu au module 2.

Une métaphore : la ville

KubernetesDans la ville
Clusterla ville
Nœudun bâtiment
Podun appartement
Conteneurun occupant
Deploymentle gestionnaire immobilier, qui veille à ce que les appartements soient occupés
Servicel'adresse postale, le standard téléphonique
Ingressla porte d'entrée de la ville
ConfigMap / Secretle règlement intérieur / le coffre
Namespaceun quartier
Pas besoin d'en faire une métaphore permanente, mais elle aide au début. On y reviendra au jour 2 pour Service, Ingress, ConfigMap, Secret, Namespace.

L'état souhaité s'écrit en YAML


apiVersion: apps/v1
kind: Deployment           # un Deployment
metadata:
  name: vote               # qui s'appelle vote
spec:
  replicas: 3              # je veux 3 exemplaires
  selector:
    matchLabels:
      app: vote            # les pods étiquetés app: vote
  template:                # fabriqués sur ce modèle :
    metadata:
      labels:
        app: vote
    spec:
      containers:
        - name: vote
          image: ghcr.io/bngams/kube-vote:1.0

On ne dit pas « lance 3 conteneurs ».

On décrit ce qu'on veut, puis :

kubectl apply -f vote.deploy.yml

Les fichiers YAML se rangent dans Git : on sait qui a changé quoi, quand, et on peut revenir en arrière.

Pas besoin de savoir écrire du YAML : savoir le lire suffit pour un chef de projet. Au TP02 ils complètent quelques trous.

Module 5

Passer à l'échelle

1 heure avec le TP03.

Qui possède qui ?

Changer replicas : le même ReplicaSet ajoute ou retire des pods. Changer le modèle (l'image…) : un nouveau ReplicaSet, c'est une nouvelle version.

Le ReplicaSet est un détail technique, mais il explique les noms des pods et préparera les mises à jour du jour 2.

Passer à l'échelle, c'est changer un chiffre

Le fichier fait foi. Un raccourci (kubectl scale) est effacé par le prochain kubectl apply. On modifie le fichier, idéalement dans Git (c'est l'idée du GitOps).
Au TP03, ils constatent eux-mêmes qu'un kubectl scale est écrasé par le apply suivant.

Les réservations : la place sur les nœuds

Les requests déterminent combien de nœuds il faut… donc la facture. Un pod Pending en production signifie souvent « le cluster est plein ».

L'ordonnanceur compte les réservations, pas la consommation réelle. Au TP03, un pod qui réserve 64 processeurs reste Pending, et les anciens pods continuent de servir.

  • Réserver des ressources, provoquer un pod Pending

Ce qu'on retient du jour 1

  • Un conteneur emporte l'application et son environnement : il tourne pareil partout
  • Une image se construit (Dockerfile), se range (registre), se lance (conteneur)
  • Docker lance des conteneurs ; il faut un orchestrateur pour les maintenir en vie
  • Kubernetes compare en permanence l'état souhaité et la réalité, et corrige l'écart
  • On décrit ce qu'on veut en YAML ; le fichier fait foi
  • Passer à l'échelle, c'est changer un chiffre ; les réservations font la capacité… et les coûts

Quiz express

  1. Je supprime un pod géré par un Deployment. Que se passe-t-il ?
  2. Je supprime le Deployment. Et maintenant ?
  3. Le conteneur plante. Le nom du pod change-t-il ?
  4. J'ai tapé kubectl scale --replicas=5, puis un collègue applique le fichier qui dit 3. Combien de pods ?
  5. Mon pod est Pending. Que faut-il regarder ?

À demain : on rend l'application joignable, on la configure, on la met à jour… et on la répare.

Réponses : 1. un nouveau pod est recréé (nouveau nom). 2. tout disparaît. 3. non, RESTARTS +1. 4. 3. 5. kubectl describe pod, section Events (souvent : plus de place). Rappeler d'arrêter son cluster en fin de journée (TP00, section 4).
